# 给 DSH 的上传提示词（可直接复制粘贴）

> 三种场景，分别复制对应段落。DSH 是本地 Agent，能执行终端命令。

---

## ⚠️ 先看这个：两个仓库的分工（架构决策）

实测结论（2026-11-16）：

```
codeload 匿名拉取公开仓  dsh-plugins  → HTTP 200  ✅
codeload 匿名拉取私有仓  std-plugins  → HTTP 404  ❌
```

**DSH Skills Manager 通过 `codeload.github.com` 匿名拉取，强制要求仓库公开。**
（其 README 原文："本仓库必须是公开仓库，否则订阅会失败"）

这与"外部人员装不了"的目标冲突。**分工建议**：

| 内容类型 | 走哪个仓 | 理由 |
|---|---|---|
| **Skill（技能）** | `dsh-plugins`（公开） | 方法论本身无保密价值；DSH 只支持公开 |
| **Plugin（插件）** | `std-plugins`（私有 npm） | 含业务逻辑/数据，必须私有 |

**技能是"怎么做"，插件是"公司的事"** —— 后者才需要保密。

> 若你要求技能也私有，那 DSH Skills Manager 这条路走不通，只能走命令行 clone + 手动复制。

## 【场景 A】上传一个 Skill（技能）

> DSH 技能 = `SKILL.md` 文件夹。存在 `~/.workbuddy/skills/` 或 `~/.dsh/skills/`。

### 提示词 A1 —— 通用上传

```
请把技能 <技能名> 上传到 DSH 插件仓库。

【仓库信息】
- 仓库：https://github.com/Zhong1856572/dsh-plugins
- 分支：main
- 目标路径：skills/<技能名>/
- 上传脚本：tools/upload-skill.sh（仓库里已有）

【执行步骤】
1. 找到技能源目录（依次尝试）：
   - ~/.dsh/skills/<技能名>
   - ~/.dsh/profiles/desktop/skills/<技能名>
   - ~/.workbuddy/skills/<技能名>
2. 校验源目录必须含 SKILL.md，且 frontmatter 里 name 字段是合法 kebab-case
   （仅 ASCII 小写字母、数字、连字符，如 my-custom-skill）
   —— DSH 宿主强制要求，不合规会提示"宿主不支持此技能名称格式，无法启用"
3. 运行脱敏：python3 tools/sanitize.py <技能目录>
4. 运行密钥扫描（脚本内置，命中即中止）
5. 提交并推送到 main
6. 同步清单：python3 tools/sync-manifest.py
   —— 这一步最容易被漏。清单不更新，DSH 扫不到技能，员工订阅后看不到。
   脚本以 skills/ 目录为唯一事实来源反向生成清单，同时会报出：
     · 缺 SKILL.md 的目录
     · 没有 frontmatter name 字段的
     · name 不是 kebab-case 的
7. 校验清单：python3 tools/sync-manifest.py --check
   （必须输出"✓ 清单一致"才能继续）
8. 更新 README.md 的"技能清单"表格

【提交信息格式】
feat(skill): 新增 <技能名>

【硬性约束】
- 不要提交任何密钥、令牌、密码
- 不要提交本机真实路径（C:/Users/<用户名>/），用 <USER_HOME> 占位
- 不要提交内网 IP（192.168.x.x / 10.x.x.x），用 <INTERNAL_IP> 占位
- 不要提交内部客户名称、报价、组织架构、人员姓名
- 不要在 push 前跳过脱敏和密钥扫描
- 不要跳过 sync-manifest.py —— 漏了这步技能等于没上传

【完成后向我汇报】
- 技能名、提交哈希、GitHub 地址
- skills/ 下新增了哪些文件
- 脱敏改动了哪些文件
- 密钥扫描结果
- sync-manifest.py 的检查结果
- 安装命令（给别人用）
```

### 提示词 A2 —— 一次性上传多个技能

```
请把这批技能上传到 DSH 插件仓库：<技能1>、<技能2>、<技能3>

【仓库】https://github.com/Zhong1856572/dsh-plugins （分支 main）
【目标】每个技能放到 skills/<技能名>/

【逐个执行】
对每个技能：
1. 定位源目录（~/.dsh/skills/ → ~/.dsh/profiles/desktop/skills/ → ~/.workbuddy/skills/）
2. 校验 SKILL.md 存在且 frontmatter name 是 kebab-case
3. python3 tools/sanitize.py 脱敏
4. 密钥扫描
5. git add + commit（每个技能单独一次提交，便于回滚）

【全部完成后】
- python3 tools/sync-manifest.py      同步清单（以 skills/ 目录为准）
- python3 tools/sync-manifest.py --check   必须通过
- 更新 README.md 技能清单表
- 一次 push

【汇报】逐个技能的：名称、提交哈希、脱敏改动文件数、密钥扫描结果
```

### 提示词 A3 —— 上传前的批量体检（推荐先跑这个）

```
请体检 ~/.workbuddy/skills/ 下的所有技能，找出哪些还不符合 DSH 的加载要求。

【检查项】
1. 缺 SKILL.md 的目录
2. SKILL.md 没有 frontmatter（开头不是 ---）
3. frontmatter 里没有 name 字段
4. name 不是 kebab-case（^[a-z0-9]+(-[a-z0-9]+)*$）
5. frontmatter 里没有 description，或 description 是空
6. description 里没有触发词（DSH 靠它判断何时启用）

【只报告，不要修改任何文件】

【输出】
按"可直接上传 / 需要改 name / 需要补 frontmatter / 需要补触发词"四类分组，
每组列出目录名、当前 name、建议改成什么。
```

## 【场景 B】上传一个 Plugin（插件，npm 包）

> DSH 插件走 npm 生态，包名要带 `dsh` 字段声明。

### 提示词 B1 —— 发布 npm 插件

```
请把插件 <插件名> 发布到公司内部 npm 仓库，供员工安装。

【仓库信息】
- 源码仓：https://github.com/Zhong1856572/std-plugins （私有）
- 目标路径：packages/<插件名>/
- 包名规则：@zhong1856572/<插件名>   ← 强制，不可改
- npm registry：https://npm.pkg.github.com
- 员工安装命令：npm i -g @zhong1856572/<插件名>

【package.json 必须包含】
{
  "name": "@zhong1856572/<插件名>",
  "version": "0.1.0",
  "type": "module",
  "main": "lib/index.js",
  "dsh": {
    "client": { "platform": "web" }
  },
  "engines": { "dsh": ">=0.2.0-rc.1 <0.3.0-0" },
  "peerDependencies": { "@deepseek-ai/dsh": ">=0.2.0-rc.1 <0.3.0-0" },
  "repository": { "type": "git", "url": "https://github.com/Zhong1856572/std-plugins" },
  "publishConfig": { "access": "restricted", "registry": "https://npm.pkg.github.com" }
}

【执行步骤】
1. 从模板复制：cp -r packages/plugin-example packages/<插件名>
2. 改 package.json（name / description / main / bin）
3. 写实现到 lib/ 或 src/
4. 同步登记到根目录 plugins.json：
   { "id": "<插件名>", "name": "显示名", "package": "@zhong1856572/<插件名>",
     "version": "0.1.0", "summary": "一句话说明", "category": "分类",
     "install": "npm i -g @zhong1856572/<插件名>",
     "requires": ["node >= 18.17"], "author": "DSH", "status": "internal" }
5. 本地自检（必须全绿才能提交）：
   node scripts/catalog.mjs
   npm test
   node scripts/release.mjs --dry-run
6. 提交到 feature 分支并开 PR
7. PR 合并到 main 后打 tag：<插件名>@0.1.0
8. 推送 tag，CI 自动发布到 npm registry

【硬性约束】
- 包名必须以 @zhong1856572/ 开头（GitHub 强制校验）
- 改了代码必须升 version，否则 CI 会阻断发布
- version 必须与 plugins.json 里的记录一致
- tag 格式：<插件名>@<版本号>，不要带 @zhong1856572/ 前缀
- 不要把任何令牌写进 package.json 或源码

【完成后汇报】
- 包名、版本、提交哈希
- PR 地址
- CI run 地址与结果
- 员工安装命令
```

## 【场景 C】新建一个技能（从零）

```
请创建一个新的 DSH 技能 <技能名>，用于 <用途描述>。

【技能规格】
- 目录：~/.workbuddy/skills/<技能名>/
- 必须含 SKILL.md
- frontmatter 格式：
  ---
  name: <kebab-case 英文名>     ← 必须是合法 kebab-case，DSH 强制校验
  description: |
    <中文描述，说明这个技能做什么、什么场景触发>
    触发词：<关键词1>、<关键词2>、<关键词3>
  category: capability
  version: "1.0.0"
  agent_created: true
  ---

【内容要求】
1. 技能正文用 Markdown，包含：
   - 适用场景
   - 执行步骤（可操作的 SOP，不是原则描述）
   - 输入输出规范
   - 常见错误的处理方式
2. 描述里必须列出触发词，DSH 靠它判断何时启用
3. 引用外部脚本时用相对路径，脚本放在同目录 scripts/ 下

【创建完成后】
- 上传到 https://github.com/Zhong1856572/dsh-plugins 的 skills/<技能名>/
- 走脱敏 + 密钥扫描
- 更新 dsh-plugins.json 和 README.md 清单

【完成后汇报】
- 技能路径、SKILL.md 摘要、提交哈希、安装方式
```

## 【补充】让 DSH 知道的两条硬规则

如果 DSH 反复犯同样的错，把这段追加进去：

```
【DSH 技能规范备忘】

1. frontmatter 的 name 必须是 kebab-case
   ✅ my-custom-skill
   ❌ 中文名、My_Skill、大写
   目录名可以是中文，但 name 必须显式声明合法英文名。

2. 仓库是公开的，提交前必须脱敏
   - 路径 C:/Users/<用户名>/ → <USER_HOME>
   - 路径 ~/.workbuddy → <WORKBUDDY_HOME>
   - 内网 IP → <INTERNAL_IP>
   - 密钥/令牌/密码 → 一律不得提交
   用 tools/sanitize.py 自动处理，别手改。

3. 技能不放业务数据
   客户名单、报价、组织架构、人员姓名一律不进技能。
   业务数据放插件（走私有 npm 仓），技能只放方法论。
```

| 位置 | 用途 |
|---|---|
| `~/.workbuddy/skills/` | 本机有 202 个技能，DSH 可直接读（当前 `workbuddy` 来源被禁用，需在设置里打开） |
| `~/.dsh/skills/` | DSH 独立技能目录（当前不存在，会自动创建） |
| `~/.dsh/profiles/desktop/skills/` | desktop profile 的技能目录 |

> DSH 设置 → 技能 → 来源管理里有个 `workbuddy` 开关（当前是停用状态）。
> 打开它，DSH 就能直接加载 `~/.workbuddy/skills/` 下的技能 —— **这可能是你真正想要的**，
> 不用逐个上传。
